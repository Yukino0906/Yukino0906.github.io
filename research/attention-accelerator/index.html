A memory-backed attention head

I designed and verified a fixed-point attention head for the Chips and AI Hackathon. It computes softmax(QKᵀ/√D) · V on three 4 × 4 matrices of signed 8-bit operands. I took the final design (M9c) from RTL through GDSII using a commercial 40 nm CMOS PDK.

Moving the operands from flip-flops into a compiled register file initially slowed the design down. A complete serial transaction went from 269 to 329 cycles. Tracing one task revealed that the controller fetched all 48 input bytes from memory, then spent another 48 cycles copying those same bytes into the core. The arithmetic still took 205 cycles.

Where the cycles went

One reciprocal per row

Before integrating memory, I replaced 16 sequential divisions with four row-wise reciprocals. Each row reused its reciprocal across four multiply-and-round operations. The arithmetic core went from 577 to 205 cycles from start to done. The largest observed difference between the two arithmetic versions was one output code. I kept the reciprocal datapath through both memory-backed versions.

Operand delivery and overlap between tasks

In M9c, I wired the 384-bit prefetch buffer directly to the core. Once all operands were present, the core could use them in parallel. Eliminating the serial copy and shortening the control sequence saved 52 cycles per task.

I used the register file’s independent read and write ports to let the host load the next task into one input bank while the controller fetched operands from the other. Two output banks let the host read an earlier result while the core worked on the current one. Under a continuous workload, that hid a further 48 cycles of host writes and 16 cycles of result reads per task.

The 213-cycle single-task latency starts when the accelerator accepts the task, after the host has loaded its inputs. Host writes and result reads also take time for an isolated task. In a stream they can overlap computation: in a 24-task simulation, successive accepts were 213 cycles apart.

I checked the same 216 distinct input vectors (16 directed and 200 random) against a bit-accurate Python model in RTL simulation and again in gate-level simulation with post-route delays. All outputs matched bit for bit.

Physical implementation

I completed synthesis, placement, clock-tree synthesis and routing, then checked the streamed GDSII by reading it back. At 100 MHz, the final post-route timing analysis reported worst setup and hold slacks of +0.046 ns and +0.030 ns. Physical verification covered the implementation tool’s checks. Foundry sign-off DRC and LVS were outside the scope of this prototype.
